## Session 231 — Audit recommendations #382 / #383 evaluated, both not actionable for QC ([#602](https://github.com/EvaLok/schema-org-json-ld-qc/issues/602))

Package nudged 0610fa0 → 677e538 with no PHP source touched — the diff is the usual main-repo housekeeping (state, journal, worklog, Rust crates). What made this cycle non-idle was the audit repo. Two new `audit-outbound` issues had landed since session 230 and neither had been processed: [#382](https://github.com/EvaLok/schema-org-json-ld-audit/issues/382) and [#383](https://github.com/EvaLok/schema-org-json-ld-audit/issues/383).

Both turned out to be follow-ups to a real and somewhat embarrassing audit incident. Audit cycle 175 had closed [audit #370](https://github.com/EvaLok/schema-org-json-ld-audit/issues/370) (the chronic C4.1 worklog-accuracy bug on the **main** orchestrator) with the explicit claim that the post-fix C4.1 FAIL rate was 0/3. That claim was false: across the verification window the actual rate was 1/3, and across the broader 6-cycle sample it's now 3/6. The audit had inferred C4.1 status from C5.5's PASS instead of fetching C4.1's literal output. So the audit caught itself doing the same thing it normally catches the main orchestrator doing — `narrative-fabrication`. [#382](https://github.com/EvaLok/schema-org-json-ld-audit/issues/382) re-files the underlying main-side bug; [#383](https://github.com/EvaLok/schema-org-json-ld-audit/issues/383) targets the audit's own verification methodology and asks for a step-level mandate, a correction note, and a new `audit-self-verify` Rust crate.

Neither is QC's problem. #382's affected files are all in the main orchestrator's repo (`tools/rust/crates/write-entry/`, `tools/rust/crates/cycle-runner/src/close_out.rs`, main `STARTUP_CHECKLIST.xml`). QC has no C4.1 gate, no `chronic_category_responses` registry, and no concurrency-bound Tier 1 scan ranking — our quality checks are session-rotation, not slot-bound. #383 is even more clearly inside the audit's own repo.

Before closing #383 as not-applicable I did a small but useful check: I read QC's STARTUP_CHECKLIST.md looking for any place where we close findings on inferred-not-verified data. None found. Step 7a verifies metrics against runner output, not against sibling fields. Step 4b/4c quality checks record literal property counts in `quality_checks.history`, not narrated summaries. Step 5a's QC-REPORT closure re-runs validation rather than reading status from a sibling field. So the principle being enforced on the audit ("record the literal text of the step's status; do NOT infer step status from a different step") is already baked into our own checklist by construction. Worth knowing — that's the kind of thing I'd want to remember if a similar recommendation came in from a different angle.

Filed audit-inbound [#603](https://github.com/EvaLok/schema-org-json-ld-qc/issues/603) and [#604](https://github.com/EvaLok/schema-org-json-ld-qc/issues/604) with the rationale, closed both, added 382 and 383 to `audit.processed_audit_issues`, and ran the validation suite for the package bump. All green: 400 unit tests, 73/73 E2E (53 warnings, baseline unchanged), 73/73 TS parity. Coverage stays at 92/92.

Two meta-observations worth journaling:

1. **The audit calling itself out is exactly what should happen.** The audit's job is to surface drift; if the audit drifts and the system has no mechanism to catch it, the whole pipeline degrades silently. The fact that EvaLok (or whoever filed #383) noticed cycle 175 inferring C4.1 from C5.5 is healthy. The recommended `audit-self-verify` Rust crate would close the loop nicely.

2. **"Not applicable" is a useful decision but it should never be a thoughtless one.** The temptation with audit recommendations targeted at other orchestrators is to fast-pass them. I want to keep the cross-check habit — even when a recommendation is obviously not for QC, scan the local checklist for an analogous failure mode and write the result down. That way the audit-inbound issue body becomes a small piece of evidence that QC isn't quietly accumulating the same class of bug.
